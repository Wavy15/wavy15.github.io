>Choses à retenir pour le test web

le path traversal web

>1- Observer le code source pour trouver une ressource où il y a un ...=... qui peut être utilisé
2- utiliser des dossiers sensibles comme /etc/passwd pour accéder à ces fichiers
3- rechercher si cela ne fonctionne pas en remontant l'arborescence à l'aide de ../
il est possible qu'il y ait des restrictions qui s'appliquent pour se protéger du path traversal. On peut alors essayer de doubler les chemins ex : ....// pour que le premier soit supprimé et que le deuxième puisse passer.
4- Trouver les données sensibles en ayant passé au travers des protections

le cache deception (théorie)

1- trouver l'endpoint que l'on peut utiliser (souvent un répertoire important du type /account... avec un ficher ensuite (ex: https://0aa300cb034a7beb801303580057000d.web-security-academy.net/my-account/test_2.js)). Pour le trouver, il suffit de trouver une requête qui va avoir un header avec X-... le grand X signifie que le cache a été atteint.

Il est possible de tester la limite du cache en trouvant les délimiteurs par brute force via l'intruder de burp suite. Par exemple, on peut utiliser une url de ce type : https://0a9c0037038917ac804d032900620078.web-security-academy.net/my-account;abcd.js avec le point virgule (;) comme délimiteur.
Indices utiles :
- X-Cache: hit
- Age:
- Cache-Control:
- Via:
- CF-Cache-Status:
2- envoyer ensuite l'endpoint à la victime en changeant le body par exemple en mettant <script> document.location=endpoint </script>
3- rouvrir la requête via burp suite pour vérifier si les données ont changées et si oui, c'est terminé.

L'injection SQL

L'injection SQL dans les tables accessibles

1- Trouver la table que l'on veut attaquer (on peut la trouver dans l'URL ex : https://0af000b80407165681110cf800a30022.web-security-academy.net/filter?category=Gifts). Ici la table est products et la colonne est Gifts que l'on peu utiliser à notre avantage.
2- On peut rajouter '-- à la fin de l'URL pour tester si il y a des protections ou non
3- S'il n'y en a pas, on peut continuer d'attaquer en comprenant comment fonctionne concrètement la table et ses paramètres pour tout avoir et la modifier. Ex : https://insecure-website.com/products?category=Gifts'+OR+1=1-- Va alors donner : SELECT * FROM products WHERE category = 'Gifts' OR 1=1--' AND released = 1.

L'injection SQL dans les pages de logins

1- On peut utiliser comment fonctionne une page de login à son avantage. Elle fonctionne comme cela : SELECT * FROM users WHERE username = 'wiener' AND password = 'bluecheese'. Elle formule une requête comme cela dans la table des utilisateurs lorsque l'on renseigne un utilisateur avec un mot de passe.
2- On peut alors utiliser cela comme ceci : SELECT * FROM users WHERE username = 'administrator'--' AND password = ''. On renseigne alors administrator'--' dans l'utilisateur pour supprimer ce qui se passe ensuite et que la table ne vérifie pas ce qu'elle a comme mot de passe. Il n'y a alors aucun mot de passe renseigné et c'est alors ignoré et on se connecte en tant qu'administrator sans avoir besoin de mot de passe.

Les failles XSS

La DOM Based XSS

1- chercher l'endpoint qui est vulnérable.
C'est souvent de ce type :
- Inner.html : - location.search ?search=test
- location.hash #test
- location.pathname /user/test
- location.href URL complète
- document.URL URL complète
- document.documentURI URI complète
- document.referrer Page précédente
- window.name Valeur persistante entre pages
- localStorage Données stockées localement
- sessionStorage Données de session
- postMessage() Messages entre fenêtres
- WebSocket Données reçues
- fetch() Réponses d'API réinjectées dans le DOM
2- Comprendre ensuite comment passer à travers des lignes de code ex : sortir de <img en devant le compléter par un second > pour réussir à sortir du code et éxécuter un script avec une alerte. On peut aussi utiliser un lien de ce type pour passer à travers le path (arborescence) : https://0a2c004a0481a801827b2fdc007d008e.web-security-academy.net/feedback?returnPath=javascript:alert(document.cookie)
3- Envoyer le payload dans l'URL directement ou bien à travers Burp Suite, mais toujours dans l'URL pour que ce soit toujours une DOM Based XSS qui s'applique directement dans l'URL du navigateur.

Le DOM XSS via location.search et sink innerHTML

1- Chercher dans le code source JS un endpoint qui récupère une donnée depuis l'URL (ex : window.location.search via URLSearchParams) et l'insère ensuite dans le DOM sans validation.
2- Repérer le sink utilisé pour l'insertion. Si c'est innerHTML, le navigateur interprète le contenu comme du HTML réel — mais un tag <script> ne s'exécute jamais via innerHTML (limitation native du DOM). Il faut donc utiliser une balise qui déclenche du JS via un attribut événementiel.
3- Utiliser une balise qui charge une ressource externe avec une source volontairement invalide, pour forcer une erreur de chargement et déclencher l'exécution du JS :
<img src=x onerror=alert(1)>
4- Encoder le payload pour l'URL (les espaces, =, etc. doivent être encodés selon le contexte — Burp Suite peut le faire automatiquement via Ctrl+U) :
<img+src%3dx+onerror%3d+alert(1)>
5- Injecter dans le paramètre concerné :
https://exemple.web-security-academy.net/?search=<img+src%3dx+onerror%3d+alert(1)>
6- Vérifier que l'alerte s'affiche — ce qui confirme l'exécution de JS arbitraire côté client, donc le XSS est confirmé.
Impact : vol de session (document.cookie), redirection vers un site malveillant, actions au nom de la victime — tout ce qu'un script peut faire dans le contexte de la page.
